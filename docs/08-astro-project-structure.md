## Decisions this locks in

**Content collections stay Markdown, no MDX.** Nothing built in Phase 2 needed embedded components inside content, and the brief is explicit that "Markdown should remain the source of truth." Don't reach for MDX unless a real, specific need shows up during chapter-writing — it's easy to add later, hard to walk back once chapters depend on embedded components.

**`book-structure.ts` stays the single source of truth for Part/chapter placement**, per the IA decision to keep chapter slugs flat. Content collection frontmatter never duplicates part/order — confirmed working in Phase 2 (`findChapterLocation` looked this up correctly for both the chapter page and the Insight's "related reading" link).

**Blog is a separate collection from chapters/insights/models**, with its own route structure that exactly mirrors the current MkDocs URLs. It does not share a schema with the book content types — a blog post has date/tags/categories; a chapter has none of those. Keeping them separate collections (rather than one big `content` collection with a `type` field) matches how differently they're queried: the blog is browsed chronologically, the book is browsed by Part.

**References has no per-item route.** Every other content type (chapters, insights, models) got a dynamic `[...slug].astro` route in Phase 2 or is planned to. References is deliberately different — one static page, because it's back matter, not a fourth parallel content type with its own permalinks (confirmed in the IA doc already).
